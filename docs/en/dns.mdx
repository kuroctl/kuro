Without DNS, players join a server with `IP:port`. With a DNS zone handed to Kuro, each server
gets a name: `survival.play.example.com`.

## What Kuro publishes

| Name | Type | Points to |
|---|---|---|
| `<node>.nodes.play.example.com` | `A` (and `AAAA`) | The node's public address |
| `<server>.play.example.com` | `CNAME` | Its node's name |
| `_minecraft._tcp.<server>.play.example.com` | `SRV` | The node and server port, if the prefab declares it |

The port stays in the address (`survival.play.example.com:25568`), since several servers share
a node's IP. Games that read an `SRV` record, like Minecraft Java, do without it: the player only
types the name.

Kuro **never** touches a record it did not create, and recreates the ones deleted by hand.

<Tip>
  **A dedicated domain.** At Cloudflare, an API token covers a whole zone. Use a domain for game
  servers that is separate from your website's: a stolen token could then change nothing on your
  site or your other services.
</Tip>

## Cloudflare

<Steps>
  <Step title="Create the token">
    **My Profile › API Tokens › Create Token**, "Edit zone DNS" template.
  </Step>
  <Step title="Limit its permissions">
    Permissions: `Zone › DNS › Edit` and `Zone › Zone › Read`, on **this zone only**. Optional:
    restrict the token to the API machine's IP address.
  </Step>
  <Step title="Give it to Kuro">
    In Kuro, **Settings › DNS**: Cloudflare provider, server domain (for example
    `play.example.com`), token, then **Save** and **Test**.
  </Step>
  <Step title="Fill in the nodes">
    On each node's page, fill in its **public address**.
  </Step>
</Steps>

Records appear within a minute, as "DNS only" (grey cloud): game traffic does not go through the
Cloudflare proxy.

## Web sites

A web prefab (WordPress…) is not published on a port: each site gets an HTTPS address under the
**web sites domain** of your DNS settings, for example `abcdefg234.web.example.com`. The
identifier is random: no collision, no misleading name. On every node that hosts a site, Kuro
runs a proxy (Caddy) that obtains Let's Encrypt certificates and relays to the site's container,
exposing nothing else.

<Steps>
  <Step title="Pick the domain">
    In **Settings › DNS**, set the web sites domain: in the same zone as the server domain,
    apart from it and from the nodes sub-domain (`web.example.com` next to `play.example.com`,
    for instance). Without it, a web prefab cannot be deployed.
  </Step>
  <Step title="Open ports 80 and 443 on the node">
    The proxy listens on ports 80 and 443 of every node that serves sites. Behind a NAT, forward
    them to the node: Let's Encrypt must reach the name on port 80 to issue the certificate. The
    installer opens these ports in the firewall of the `node` role.
  </Step>
  <Step title="Check">
    On the server page, the site address is clickable and its status tells whether the proxy
    runs and the certificate is issued.
  </Step>
</Steps>

<Warning>
  **Same domain as the panel.** A site hosted under your domain is "same site" as the panel for
  a browser. Kuro protects itself (`__Host-` cookie, checked origin), but a host that opens sites
  to third parties should register its sites domain on the
  [Public Suffix List](https://publicsuffix.org/): each site then becomes a registrable domain
  of its own, for browsers as for Let's Encrypt limits (50 certificates per week and registered
  domain). Registration takes several weeks.
</Warning>

A machine that runs both the API and a node already has Caddy on ports 80 and 443: do not serve
sites from that node, or change the proxy ports (`[web]` in `daemon.toml`, `http_port` and
`https_port`) behind a redirection. Under rootless Docker, the installer sets
`net.ipv4.ip_unprivileged_port_start` so the proxy can bind these ports.
